Dispatch

The bytes and the order of writes that make the hardware run one kernel.

A dispatch is four objects. The kernel object holds the descriptor and the code. The kernarg buffer holds the address the kernel writes to. The signal counts the packet down. The packet points at the other three. The descriptor is the dangerous one, because its fields tell the hardware how many registers each wave gets and how the wave starts. A wrong bit there resets the GPU. So the assembler builds the descriptor from the directives in the source, and rbg patches exactly one field, the entry offset that the assembler leaves as a relocation. Nothing else in those bytes is hand made.

The packet is built in one order, and the order is the mechanism. The body goes down first. The header goes down last, as a single store after a release fence, so the command processor can never read a half built packet behind a valid header. The write pointer then moves on by one. The doorbell takes the packet index, not the next index and not the ring slot. Coherent memory lets the command processor find the packet from the write pointer alone, so a packet can run with no doorbell at all. Ring it anyway. The doorbell write is the one place in the program that starts hardware, and the code says so in a comment.

The first kernel is store42. It loads the target address from the kernarg pointer, stores 42, waits for the store, and ends. Nine instructions and 36 bytes. The tool tools/asm runs llvm-mc and llvm-objcopy to pull out the text and the descriptor, and both are committed, so a clone without LLVM still builds. On the first run the target became 42. The signal did not reach zero. The kernel ran and the completion path did not, and the next page takes that apart.
