Method

How the work was done: one-page prompts, a small local model in a loop, and a person at every GPU gate.

A 27B local model (Qwen) running in a coding agent wrote the implementation, one unit per one-page prompt. A larger model drove: it planned the units, verified each fact in kernel and ROCm source, reviewed every handoff, and bisected the hangs. The owner ran every GPU step by hand and decided at every gate. The method exists because the small model has a small context and the GPU has no undo.

Docs carry the shape: 80 columns, 60 lines, story shape, and no repeat of a fact another page owns. A checker in sh and awk enforces the first two rules; a person reviews the rest. Agent reports obey the same rules. AGENTS.md holds the rules that failures bought. Read files by line range and pipe build output through tail, because context is the scarce resource. Never create a GPU queue from inside an agent session, because the agent's own model shares the GPU and a hang ends the session. Report a wrong doc fact as stale; never fix it or trust it. A prompt is a thin launcher: verified facts, a goal, a verification loop, and a handoff that rewrites STATUS.md with one of four states: done, in progress, ready for GPU test, blocked. tools/drive reads that line and starts the next session until the unit is done or a person must act. One extension hands off at 40k context tokens instead of compacting, because prompt processing runs at about 200 tokens per second and a long context costs minutes per turn. Another extension nudges the model when a turn ends with reasoning and no action.

The rules that cost resets take one line each in docs/lessons.md, with the date: EOP required; COHERENT on the CP buffers; 8 spare VGPRs; no new mapping while another process is busy; one run first. Two facts read from source were wrong for this hardware. Reading finds candidates, and only a run settles them.
