Completion

How the command processor reports a finished dispatch, and the two faults that stopped it.

Two faults stood between a kernel that ran and a command processor that said so. The kernel accepted both. The hardware refused both, and this hardware refuses by hanging, which costs a GPU reset.

The first fault was the end-of-pipe buffer. The ioctl comment calls it optional, "not required for all ASICs". The gfx11 MQD code programs its address and its size into the hardware queue descriptor with no zero check. A queue built without one hangs MES on REMOVE_QUEUE at destroy time. That cost four resets, and each reset killed a local model server that shared the GPU. The fix is a 4 KiB coarse EXECUTABLE buffer, the same buffer libhsakmt allocates.

The second fault was the memory type. The kernel ran and the target held 42, but the completion signal stayed 1 and the queue could not be removed. No page fault was logged. ROCr allocates every buffer the CP touches fine-grained, which is COHERENT, and ours had none, so the CP reads and atomics did not see the bytes the CPU wrote. The fix is COHERENT on the ring, both pointers, the kernel object, the kernarg and the signal. That cost five resets before the fix, and five clean runs came after it.

One earlier fact fell with this fix. When the memory is coherent, the CP polls the write pointer, and a packet runs without a doorbell. The older note said that only the doorbell starts a packet. That note was an artifact of non-coherent memory.

Each fix came out of reading the sources. kfd_mqd_manager_v11.c gave the EOP rule. ROCr amd_aql_queue.cpp and libhsakmt fmm.c gave COHERENT in the system allocator. The rule from here is to mirror what ROCr allocates, not what the ioctl permits. The other rule is that the first GPU run of a new kernel is one run, because five identical runs cost five resets and taught the same thing once.
